# Internal Runtime DOX

## Purpose

- Own the provider-neutral runtime, channel adapters, harnesses, durable state, extension hooks, workspace initialization, and markdown orchestration.

## Package Ownership

- `app` composes screens, live settings, channel and harness supervisors, histories, commands, hooks, orchestration, captured runtime logs, startup registration, conversation branching, compact durable-work listings, and the active agent-job registry. Jobs retain one bounded race-safe structured execution snapshot; live execution state, workflow phase, durable outcome, and evidence-based health remain distinct. Health uses structured lifecycle or lease evidence only; elapsed text silence never implies a stall, and `stalled` requires an explicit provider signal.
- `agentdocs` owns curated offline behavior topics, stable references, deterministic bounded pagination/search, versioned structured output, prompt guidance, and concise `/help` topic metadata. It never reads workspace or runtime state.
- `channel` owns the common transport contract, hot-reload lifecycle supervision, and TUI, Telegram, and WhatsApp adapters. The TUI owns a narrowly scoped MIT-licensed Bubbles v0.21 textarea derivative because the upstream private wrapper splits fitting extended graphemes; keep its editor behavior aligned with that dependency while preserving grapheme-atomic wrapping, navigation, deletion, and character transposition.
- `cli` owns public command parsing and process lifecycle.
- `config` owns canonical `.spynel/config.yaml` defaults, workspace-root-relative path resolution, strict current-schema validation, and the fixed `.spynel` state root.
- `core` owns messages, responses, stable cross-package value types, and the shared compact count formatter used by constrained status indicators.
- `extensions` owns executable hook discovery and Git installation.
- `fsx` owns cross-platform atomic file replacement and no-clobber publication of complete new files.
- `history` owns independent append-oriented channel history, explicit per-conversation clearing, bounded context rendering, disk-backed discovery and latest-conversation selection, and point-in-time branching into a requested target channel.
- `instructions` owns fixed-role, bounded, UTF-8-safe loading and final prompt sections for workspace-local standing agent behavior. It never derives paths from messages or workflow evidence and never logs file contents.
- `instance` owns cross-platform workspace-server election, lock-free discovery of atomically published authenticated rendezvous records, five-second renewal, 30-second stale detection, fenced stale takeover, and expiring target-specific handoff.
- `localapi` owns the private authenticated loopback contract through which every TUI and plain CLI client identifies its caller instance, reaches the elected application service, streams messages, obtains typed status, and observes bounded shared state.
- `markdown` owns GitHub-flavored Markdown rendering for ANSI terminals, including standard OSC 8 hyperlinks for explicit absolute-file and URI links, and conversion to Telegram HTML or WhatsApp-native formatting.
- `media` owns bounded streamed attachment storage, validated outbound file directives, serialized local Parakeet transcription through miniaudio/Ogg-Opus/sherpa-onnx, and the coordinated versioned per-user cache for automatically managed speech models.
- `orchestrator` owns typed task review policy, task implementation/review and goal planning/review scanning, task-goal round linkage, atomic Markdown claims, phase leases, orphan/stale recovery, transition enforcement, goal review gating, waiting wakeups, the primary-owned semantic workflow heartbeat, persisted notification-agent actions, shared terminal-control-safe notification normalization, and durable outbox delivery.
- `harness` owns the harness interface and follow-up capabilities, centralized catalog/factories, transactional runtime supervisor, Codex app-server, Claude Code print mode, Pi JSONL RPC, and shared stable-v1 ACP stdio implementations, plus startup/earliest-negotiation diagnostics and portable test-binary provider fixtures. Queue-mode chat bursts are batched without merging job-control boundaries.
- `shortid` owns compact eight-alphanumeric-character rendering of opaque IDs for human-facing output; full identifiers remain authoritative internally.
- `startup` owns reversible, workspace-specific systemd, launchd, and Windows Task Scheduler registration.
- `theme` owns validated, file-backed semantic color palettes, embedded YAML assets, and no-clobber installation of editable workspace copies.
- `updater` owns npm-install detection and ten-second registry checks.
- `workspace` owns initialized filesystem structure and embedded, user-overridable workflow templates; it delegates built-in palettes to `theme`.

## Local Contracts

- Avoid package cycles by keeping cross-boundary values in `core` and interfaces beside their consumers.
- Configuration changes from forms and commands share the typed `config.Setting` catalog, are validated as a complete transaction, persist through an atomic `0600` replacement, and publish only the newest snapshot. Never place secret setting values in status output, framework replies, or durable conversation history. Telegram and WhatsApp fail closed: neither can be enabled without a valid canonical sender whitelist, neither can replace that whitelist with missing, malformed, punctuation-only, or normalization-empty values while enabled, and each adapter resolves the current live list at supervisor preflight, startup, every inbound event/queued message, and every pairing, provider, or proactive-delivery boundary. Invalid authorization reports and retains a connection error before downstream history, media, activity, commands, agent dispatch, replies, attachments, or hooks; it wakes the active adapter loop so Telegram closes polling/webhook service and WhatsApp disconnects, while the supervisor does not retry the unchanged invalid fingerprint or live authorization loss. The supervisor revokes stale instances before cancellation; Telegram's sole post-revocation provider exception is teardown-only `deleteWebhook`, which prevents a stopped local listener from remaining registered. Enabled Telegram webhook mode additionally requires header-secret verification, and connection status must never expose its public URL or per-token path. Normalize WhatsApp allow-list comparisons to canonical international digits so `+`, `00`, spaces, and punctuation are equivalent while letters and values beyond 15 digits are invalid; in self-chat mode resolve an incoming LID to the paired phone-number identity before authorization and conversation keying. Telegram accepts positive IDs or ASCII letter/digit/underscore usernames and links the whitelist description and wizard to the third-party `@userinfobot` helper for discovering numeric user IDs.
- WhatsApp socket reachability before device linking is pairing readiness, not a connected channel. Report `connecting` with pairing detail until the credential store has an authenticated device ID; only a paired connection may report `connected`. A connected status may expose the validated phone-number JID as `+<number>` with its official `https://wa.me/<number>` link in the TUI WhatsApp status section; never expose opaque LIDs or non-phone JIDs as account identities. Never expose QR render data on the general WhatsApp settings screen: retain it only for the pairing wizard's dedicated fullscreen QR action.
- Identify new WhatsApp QR-linked devices as `Spynel` with desktop companion metadata and an Electron QR client type instead of whatsmeow's generic unknown-device defaults. Keep phone-number code pairing on a server-accepted browser/OS display name because WhatsApp rejects arbitrary values there. Existing linked-device records retain the identity captured when they were paired.
- Persist every harness scalar in the `harness` configuration group: `name`, optional `model`, `sandbox`, `chat_agent_prefix`, `developer_agent_prefix`, `reviewer_agent_prefix`, `heartbeat_agent_prefix`, `reviews`, and the custom ACP fields. All agent prefixes default empty; optional harness-native commands such as `/goal` are validated and applied live after outer trimming with exactly one ASCII space before the original prompt, while empty prefixes preserve that prompt byte-for-byte. `reviews` accepts `skip-trivial`, `always`, or `never`, applies live and deterministically overlays task review state without disabling mandatory goal outcome review. The catalog includes native `codex`, `claude-code`, and `pi` profiles plus named ACP profiles with fixed executable arguments; only custom `acp` persists `harness.acp_command` and a shell-free `harness.acp_args` list. Require exact current profile, sandbox, and review names after lowercasing and trimming edge whitespace. Initialization probes non-custom profiles in catalog order from `PATH` and conventional per-user locations. Default `harness.sandbox` to `danger-full-access`, expose the validated `danger-full-access`, `workspace-write`, and `read-only` choices, and apply runtime-harness changes transactionally only while idle. Derive built-in executables, every working directory, approval policy, network flag, and default effort internally.
- Every settings surface formats and parses the custom ACP argument list through one deterministic one-line command-text grammar with quoting and escaping but no shell expansion; canonical YAML and runtime remain string vectors passed directly to the process.
- Interactive `spynel init` and confirmation from the uninitialized-directory screen continue into harness setup/welcome/chat in the same process. Bare interactive startup from an uninitialized child of an initialized workspace must choose the parent (default), initialize locally, or exit before primary election or workspace mutation; choosing the parent first aligns process CWD to its canonical root. Explicit config targets and noninteractive commands never wait for that choice. `spynel init --no-start` is the non-interactive/scripted initialization contract.
- `spynel send` uses a named durable `cli` history/harness session through the elected application service when one is running, or a one-shot local service otherwise; it never starts continuous orchestration. Accept bounded stdin, repeatable private attachment copies, response-delta streaming, and NDJSON event output. Default final-only output prints the last assistant-message item when the harness exposes one, while `--stream` and `--json` preserve the complete event sequence and durable history retains the aggregate turn. `spynel followup` is strict: it may steer or queue only an already-active execution for that CLI conversation and must fail before persistence if none exists. `spynel status` returns the same typed non-secret indicators as `/status`. `spynel conversations` lists bounded disk metadata, reads bounded tails, and point-in-time branches any saved channel history into an independent `cli/resume-<short-id>` conversation. `spynel command` and concise aliases route every non-visual shared slash command through the same service and extension hooks; when no owner exists they must not start a coding harness merely to execute deterministic framework behavior. TUI-only themes, titles, onboarding, ownership promotion, resume screens, and process exit remain excluded.
- The embedded communication prompt keeps the chat session responsive: answer questions and bounded status requests directly, create or refine single-objective task documents, create or refine measurable multi-round goal documents, avoid substantive implementation and foreground subagent work, and retain unfinished earlier coordination when a follow-up is steered into the active turn. `/task` and `/goal` load separate user-overridable creation directives, preserve the literal user message as delimited data, and dispatch the combined prompt through that same communication harness session. Inject the live task-review mode outside user-overridable templates and prepend the role's live harness-native prefix only after all prompt transformations, immediately before sending. Perform routine bounded inspection without narrating tool steps or announcing intended checks. Ordinary question, status, and delegation turns emit exactly one brief, natural, outcome-first result with no preamble or progress messages. Current requests and applicable safety/DOX contracts always take precedence.
