# Conversation History DOX

## Purpose

- Own append-oriented per-channel conversation history, bounded context rendering, discovery, clearing, and point-in-time branching.

## Local Contracts

- Keep each channel/conversation independent, store complete durable JSONL with private permissions, and tolerate only explicitly handled tail corruption.
- Build prompts backward from disk under both message and character limits; locate and project oversized body records with bounded memory, retaining newer messages and explicit excerpts instead of failing the conversation. Never load an unbounded history to compute bounded context.
- Branch into a new conversation without mutating its source, retain bounded reply references, and exclude private attachment contents from records.
- Append a recovery baseline to every branch so copied source messages remain context only and can never become stalled-message candidates in the new conversation.
- Retention uses the last durable entry timestamp, falling back to file modification time only for empty histories; delete only strict pre-cutoff regular files and preserve explicitly protected live conversations while reporting per-item failures.
- Recent-authorized proactive routing reads a content-free durable latest-`user` activity sidecar per conversation, ignores assistant, notification, and delivery-ledger entries so delivery cannot select itself, and ignores sidecars without a corresponding history. This sidecar is only the minimal channel-resolution primitive; it carries no reminder policy or state.
- Keep source-message identity, local acceptance time, provider-neutral admission, logical execution, exact terminal/cancellation coverage, retrigger reservation, and local recovery-display facts append-only and private. The recovery activation marker is forward-only: create it without reading or rewriting existing histories, and compare it to local acceptance rather than transport-provided message time so delayed newly admitted messages remain eligible; missing or pre-activation correlation is categorically ineligible. Recovery reads complete retained history in bounded pages of up to 2,000 recent records and 8 MiB of raw input, allowing a single larger body record to make progress. Each page validates the whole file and resolves exact terminal, cancellation, reservation and admission facts, including old timestamps and baselines, before returning. Large body strings are projected to 32 KiB while validating their complete syntax; correlation metadata remains exact under a 4 MiB structural bound. Atomic reservation reads only the requested sources without a lifetime or recent-window count cap. Discovery advances lexically through 100-conversation pages and at most 20 admissions per pass; each conversation admits at most 20 sources per turn. Deferred conversation/dispatch batches coalesce an immediate continuation; later scans continue remaining sources without duplicating reservations. Recovery prompts contain at most 48 KiB of body excerpts with an authoritative history path and instructions to read complete source messages before acting. Durable source-link inspection streams directory batches and bounded YAML headers, retaining only matches for the current candidate set instead of rejecting large task inventories. Corruption anywhere still fails closed. Both history passes hold the append lock: I/O and lock duration grow with retained history, and multiple pages repeat validation. Duplicate-identity and notification-ledger checks share strict streaming body projection with recovery and validate complete retained history with bounded per-entry memory and fail closed on corruption or unreadable entries; recovery's entry-count limit must never block new messages or framework commands in a long conversation.

- Own committed integration event replay and atomic bounded resynchronization snapshots. Cursors bind workspace/conversation, first history record and exact preceding record; invalid, cleared/replaced, corrupt, missing or excessive-lag cursors fail explicitly. Replay at most 256 raw records/4 MiB per read; snapshots pair the newest 100 visible entries under the existing 2 Mi-rune bound with the same append-lock cursor. A first subscription to an empty conversation appends only a private correlation baseline. Deltas/statuses are not durable subscription events, private ledgers stay hidden, notifications retain their existing outbox identity, and ordinary history retention/clear remains authoritative.

- Notification delivery-state lookup recognizes committed assistant and pending-TUI entries by stable event ID. The application uses that existing ledger for local, remote and explicit-fallback retry suppression; normal context rendering retains notification timestamps/assistant semantics and hides send/failure bookkeeping.
- `AppendOnce` persists an assistant/error/correlation effect and its private receipt in one synced record. Matching retries confirm durability without another append; changing any effect field except its retry timestamp fails closed. Read complete metadata with bounded body projection and reject corrupt or incomplete tails, including corruption after an existing receipt. Receipt identity/hash stay out of rendered context and committed event projections. The elected consumer must hold its exact cross-process ownership fence; a Store mutex alone is process-local. This primitive is not an arbitrary external-effect transaction or a replacement for notification delivery identity. Receipt lookup scans retained history; clear/retention remove its receipts along with the effects.

- HasUserSourceIDs checks a bounded requested source set in one complete streaming validation pass; missing sources fail and corruption after a match still fails closed. Single-source duplicate admission uses that same owning implementation. This existence check does not reserve a source or prove provider admission.

- AdmitConversation validates up to 1024 sorted unique sources against complete retained history and syncs one private admitted_sources batch plus its retry receipt in one record before provider Send. Ordinary sources must exist after the last baseline and be neither admitted nor covered; recovery sources require an existing uncovered retrigger reservation that has not already admitted recovery. Matching receipt confirmation is idempotent even after later settlement, changed receipts fail, and corrupt/incomplete history fails closed. Batch admission marks every source admitted without creating terminal coverage and stays absent from prompt/committed-event projections. The caller must hold exact cross-process ownership; this does not prove provider delivery or implement follow-up rollback/cross-worker recovery. Lookup uses the existing complete-history bounded-memory scans; index only if measured admission cost requires it.

- On visible replies, `Recovery` is the private local asynchronous presentation marker for stalled-message or retained-worker results, not a provider-admission classification. Retained partial output carries `Continues` so its display does not settle execution activity; private admission records keep their existing recovery-reservation meaning.

- `ReadDisplayEntry` shares the bounded streaming history parser with correlation readers, preserving exact metadata and complete UTF-8 runes in body excerpts. Display readers require a complete newline-terminated record, count every consumed byte including blank prefixes, and retry incomplete appends without advancing their offset. Omitted bodies have an explicit excerpt notice; full JSONL remains unchanged. Validate omitted suffixes and fail closed on corrupt or structurally excessive records.

- `AdmitRecoveryConversation` shares admission identity/receipt validation and writes retrigger reservation plus admission in one synced record. Require the forward activation and recent window, validate every exact source against complete history, and reject any covered or previously reserved source. Run the owning application policy validator under the append lock before writing; it must not reenter history or acquire worker/election ownership. Any invalid member refuses the whole batch without reservation. Matching receipts confirm without rerunning policy or creating another admission. This does not prove provider delivery or authorize retry after an unknown Send.
