# Application Service DOX

## Purpose

- Compose the provider-neutral application service used by channels, local API clients, CLI commands, configuration screens, and background orchestration.

## Local Contracts

- Keep channel/harness supervisors, histories, commands, hooks, configuration, startup registration, conversations, runtime logs, durable-work lists, and agent jobs behind the shared service boundary.
- Allocate each admitted job a durable workspace-local number from 1 through 9999 under a cross-process lock and atomically replaced counter, wrapping from 9999 to 1. Fail admission before provider dispatch when the counter or initial archive cannot be persisted; never substitute a process-local public number. Preserve the number through recovery and archival, but reopen an archived workflow job only for the same durable work ID, job kind, workflow phase, and phase claim attempt after acquiring its nonblocking cross-process ownership lock; a still-owned matching archive is an overlapping execution and must receive a new number, generation, and private identity. Later phases and attempts are also distinct jobs. After reuse, numeric lookup and the public live listing select only the newest generation; admitting or finishing an older recovered generation never shadows, removes, or exposes it in place of a newer generation. Private collision-proof archive identities and process-local execution handles keep older live or retained records isolated. Persist bounded ordered redacted event output as atomically readable snapshots, compatibly read legacy `live_alias` archives, and keep archive text inspection-only so it cannot influence workflow state.
- Treat successful channel or loopback admission as workspace-operator authorization for global runtime jobs and durable task/goal inspection. Do not add conversation, creation-channel, or notification-origin filtering inside job list, inspection, message, ping, kill, or workflow-list handlers; keep public projections bounded and free of conversation identifiers and prompt text.
- Keep `/new` as a durable TUI conversation-identity switch with the ordinary welcome screen, and route `/trigger` and manual/automatic cleanup through shared scheduler and retention boundaries rather than command-specific workers. Protect every conversation leased by an authenticated live TUI; serialize startup registration and resume branch creation-through-registration with cleanup through history deletion, retain prior identities briefly across screen switches, expire crashed-client leases before cleanup eligibility, and fence cleanup for one lease duration after owner acquisition so live clients can renew into the replacement owner's registry.
- Protect shared state and job snapshots for concurrent readers; distinguish execution state, workflow phase, durable outcome, and evidence-based health. Text silence alone is never a stall signal.
- Project the orchestrator's bounded authoritative nonterminal task/goal census and its bounded diagnostics into shared TUI state; do not derive durable work from jobs or histories.
- Project live background activity from the process-local orchestrator job registry only. Starting, running, reconnecting, recovering, degraded, and audit executions are live; terminal, cancelling, finishing, error, and explicitly stalled records are not.
- Reserve cancellation before interrupting so synchronous provider termination is captured. Count concurrent reservations by stable job identity, and restore runtime/archive plus durable control state only when every matching request failed; one failed request must never undo another accepted cancellation. After acceptance, retain the cancelling job and archive until the provider emits a terminal event so that event remains inspectable; use a bounded grace fallback for providers that never release.
- File-lock implementations remain platform-specific, captured logs remain bounded, and configuration changes validate, save, reload the canonical file into shared memory, then invoke only required cached-runtime hooks. Model persistence and harness dispatch admission share one commit fence so no post-commit dispatch observes the previous model; harness implementation and sandbox replacement remain idle-only.
- Notification-agent jobs are ordinary asynchronous harness jobs started directly from qualifying task transitions. The agent receives the task and ordinary CLI guidance, owns the decision, and edits task progress itself; application code never interprets provider output or writes a notification result.
- Heartbeat and notification jobs remain live after asynchronous provider admission until the first authoritative terminal final/error event, cancellation, or bounded timeout. Record their complete accepted event streams; an admission status such as `Codex turn started` is never completion, and late/duplicate terminal events cannot finish a job twice.
- Assemble every ordinary, `/task`, and `/goal` communication prompt through the same framework chat-guidance path so preserved custom templates retain the evidence-grounded honesty contract exactly once before role-specific persistent instructions are appended.
