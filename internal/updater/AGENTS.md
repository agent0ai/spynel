# Updater DOX

## Purpose

- Own npm and standalone installation detection, bounded release checks, verified bundle installation, and cross-workspace process restart/shutdown coordination.

## Local Contracts

- Bind npm detection to the running executable in the validated package vendor tree. Script ownership comes only from the installation-local `.spynel-install` and immutable release `.bundle.json`, never workspace state or inherited npm metadata. Unmanaged archive/development executables remain unmanaged.
- Resolve and retain the process executable during package initialization, before an update can switch an invoked symlink. Every later detection validates that retained bundle and its running version; never re-detect the old process against the new launcher target or relax version validation to recover ownership.
- npm proactive checks require the supervising launcher's explicit interactive eligibility and reuse its bounded timestamp/version snapshot. A script-installed TUI receives eligibility from the actual interactive CLI launch, ignores inherited npm snapshots, and uses the same asynchronous ten-second check and at-most-hourly refresh. Noninteractive, automatic-startup, and explicitly suppressed launches never check proactively.
- GitHub checks use the stable latest-release endpoint; reject drafts, prereleases and invalid versions. Trusted mirror overrides are `SPYNEL_GITHUB_API_URL` for discovery and `SPYNEL_DOWNLOAD_BASE` for matching assets. Production defaults use the canonical repository over HTTPS. Bound download time, bytes and redirects; refuse HTTPS downgrades.
- `InstallArchive` is the shared native boundary for `install.sh` and explicit GitHub updates. Verify the exact checksum and reject unsafe/duplicate paths, links, special files, oversized archives/trees, missing libraries/licenses, compression errors, or a candidate whose bounded `--version` execution fails. Never execute an unvalidated candidate during an update.
- The POSIX bootstrap first verifies checksums and archive paths/types, then streams only exact executable/library members to fixed temporary paths. That verified runtime invokes `install-bundle` to perform complete validation and installation. Its first supported release must include this entry point.
- Install only into a new/empty or marked per-user root. Serialize publication with a nonblocking OS file lock that releases on crash. Interrupted staging/downloads are inert. Publish a new immutable `releases/<version>-<unique>` directory and atomically replace `current`; never overwrite existing bundles or unrelated launchers, and reject downgrades even after a concurrent update.
- Keep `<root>/spynel -> current/spynel` stable. Resolve restart and automatic-startup through it even when `os.Executable` names an older bundle. Retain old bundles and inert interrupted stages; explicit uninstall stops every process using the installation. Do not add speculative process garbage collection.
- `/update` downloads/validates/switches script bundles before requesting the existing graceful shutdown/restart path. Failed validation leaves the active bundle usable. npm replacement remains exclusively in the supervising launcher after Go exits. Workspace election/job shutdown and saved state retain their existing owners.

- `Uninstall` validates installation ownership, serializes against publication, asks startup ownership to remove matching restart registrations, then terminates processes by their actual executable path (TERM followed by bounded KILL). Remove only marked runtime content and exact launcher links; preserve workspace data and unrelated siblings. npm removal accepts a validated global package even after failed postinstall and delegates package/link removal to `npm uninstall --global --prefix` for that exact prefix. Use shared verified registry discovery and native Linux/macOS inspection so unreadable live registrations fail closed and supervisor suppression precedes executor stop; never kill by process name or command-text substring.

- Own the per-user OS-config `spynel/processes` registry of private PID/generation/executable/installation/version records for live servers and TUIs. Verify native executable identity before signals; use a new registration generation at the target version with application readiness as restart evidence. Coordinate every registered instance of the selected installation across workspaces, preserving terminal descriptors through exec. Reject pre-coordination processes explicitly. `KillAll` uses the same verified discovery across installations and shares bounded TERM/KILL termination with uninstall; startup service shutdown is a supplied owning-layer callback.
- Reconcile the kernel PID snapshot with atomically published registrations before classifying an unregistered process: perform one shared two-second grace and refreshed inspection for a snapshot containing unknown instances. Confirm liveness before retaining unknowns; still reject live unregistered applications after that bounded transition window. Never infer helper roles from arbitrary arguments.
- Register native stderr readers and exit recorders with `diagnostic_reader: true` and private provider guardians with `provider_guardian: true` in the same process registry. They retain verified executable/installation identity for kill/uninstall discovery, but never acquire application readiness and never block update preflight or become restart targets; their owner closes their lifetime pipe during ordinary restart. Guardians stop/join direct providers; helper processes are never application restart targets. Unknown/unregistered application processes retain the existing fail-closed preflight rule. Do not classify helpers by parsing arbitrary command arguments or hide them from process shutdown discovery.

- The current npm wrapper explicitly advertises coordinated-update protocol 2 for native supervision and latched asynchronous shutdown; older protocol 1 is not sufficient. Bind that capability to validated launcher ownership and include it in process registration; an older wrapper supervising a newer native executable must fail preflight with one-time stop/relaunch guidance instead of silently using the old single-process update protocol.
- Register private full harness workers with `harness_worker: true`, retaining native PID/start/generation/executable/installation identity for verified kill/uninstall. They are neither application restart targets nor readiness evidence; exact known-compatible protocols are preserved, and other protocols require authenticated idle replacement. This helper classification alone does not enable application adoption or complete worker-preserving update coordination.
- `VerifyProcess` exposes the same read-only native identity check used before registered signals, so worker discovery cannot invent a separate liveness rule. Confirmed dead/zombie/absent processes return ESRCH; unreadable live state or a changed executable/start/generation remains an error, never replacement authority. It never sends a signal or changes a registration.
- Recheck native liveness after failed identity reads so a concurrent exit is reported as confirmed death. A missing live registration is distinct from a changed generation and authorizes neither a signal nor worker replacement. Native ESRCH/ENOENT during an identity read while liveness remains unconfirmed is also distinct from death or signal authority. Shared stop/uninstall waits within its existing shutdown bound for these targets' confirmed exit; a supervisor must still acknowledge suppression or exit before dependent teardown. Stop waits revalidate native identity and registration before escalation, and unreadable or changed live identities fail closed.

- Shared OS liveness excludes only confirmed dead/zombie processes: Linux reads state/start ticks from `/proc/<pid>/stat` and binds live start identity to the kernel boot ID, macOS uses `kern.proc.pid` state/start time. Signal-zero permission denial and unreadable/unknown state never establish death. Keep unreadable live registrations explicit, preserve their files, and bind new registrations to kernel start identity alongside generation/executable checks before signals; stop waits also fail closed on unverifiable live targets. New records retain `start_time` so stale same-image PID reuse fails shared discovery directly, before any fallback can discard installation identity or depend on path aliases; affected 0.13.3 records lack it and retain their existing executable/generation checks plus a kernel-start snapshot for the coordination interval. No atomic cross-platform PID-signaling guarantee is claimed.

- Native process discovery must retain visibility after npm unlinks a running image. On macOS, use the retained executable-path field from `kern.procargs2` when `proc_pidpath` loses the vnode path; never expose its arguments or environment. An unreadable live registered process is an explicit error, never an omitted restart target.

- Represent native logical instances with supervisor and linked executor PID/generation roles in this registry, verified against actual parent/image relationships. Restart only the supervisor or a direct externally managed executor. A supervised restart succeeds only after the same supervisor PID publishes a new generation and a verified ready executor at the target version; absent children remain visible and cannot count as ready. Include lawful election expiry in the 60-second restart deadline. Stop/uninstall acknowledges parent suppression before child teardown, fences generations, and gives the parent time to reap before forced parent termination.

- Register finite application CLI requests and event subscriptions as `application_client: true` at the public command boundary. They retain exact native start/generation/executable/installation identity for stop/uninstall, but never become application restart targets, readiness evidence or legacy-preflight blockers. Unknown/unregistered applications still refuse coordination; do not infer client roles from arguments.

- Worker registrations publish the shared core protocol and private installation-update socket/credential, excluded from ProcessRegistration JSON used by strict worker wire/rendezvous identity. All registry writers preserve these fields; never expose credentials in logs or release evidence. CheckRestartableFor preserves exact known-compatible workers and otherwise checks the independent authenticated idle endpoint. BeginWorkerUpdate holds one private OS lock per installation across all workspaces and pauses idle incompatible/unknown workers under their existing operation gate. Worker launch waits cancellably for the shared lock for at most one minute so a successor restarting during worker retirement can finish startup, then refuses a superseded installed version. Finish retires paused workers only after publication, confirming native death before restart; failure resumes an unchanged installation, while a changed/uncertain installation retains its pause for a verified successor coordinator. The npm parent owns the lifetime pipe across package replacement; EOF aborts, commit retires. Compatible installed coordination may recover an earlier pause without replacing active work. Old workers missing this endpoint retain one-time drain, explicit stop, external upgrade and relaunch. Available GitHub targets remain unknown and therefore use idle replacement. Native PID/start/generation/installation checks, installer validation, supervisor readiness and ordinary harness-lock cleanup remain mandatory.

- Native registrations advertise participation in the installation worker-launch gate as registry-only metadata. Unknown/incompatible replacement refuses an older application without that capability, even if it currently has no worker, so it cannot launch an unfenced predecessor during publication. Known-compatible restart behavior remains unchanged.
