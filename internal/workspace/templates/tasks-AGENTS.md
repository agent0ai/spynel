# Task Workflow DOX

Task documents use YAML front matter followed by a human-readable body and progress log.

Spynel owns `first_assigned_at` and `provider_iterations`: the former is set on the first real claim, while the latter increments under a cross-process lock immediately before each provider dispatch, recovery, control, or continuation. Agents must preserve both fields and must not repurpose phase-specific attempt counters as provider iterations. Implementation claims increment `attempt`; independent review claims increment `review_attempt` and never change `attempt`.

Required front matter: `id`, `title`, `status`, `created_at`, `updated_at`, and boolean `review_required`. Older files without the policy require review. Malformed values are unsafe and must never permit direct completion. A goal-derived task also requires immutable `goal_id` and integer `goal_round`. The task-to-goal reference is authoritative; standalone tasks omit both fields. Moving files never changes identity.

Default statuses:

- `todo`: eligible for dispatch.
- `working`: atomically claimed for implementation and backed by an implementation lease.
- `review`: implementation is complete and awaiting an independent fresh-session review.
- `reviewing`: atomically claimed from `review` and backed by a distinct review lease.
- `waiting`: blocked on a concrete external condition; document that condition.
- `done`: requested outcome completed under its review policy; independently reviewed acceptance is distinguished from permitted direct low-risk completion.
- `failed`: processing cannot continue; document evidence and recovery options.
- `cancelled`: deliberately stopped without completion; document the authority and reason.

An agent must update the document before moving it. Do not silently declare success in chat while leaving the durable task stale.

The configured `harness.reviews` mode governs task policy. `always` forces every task through independent review and `never` forces the direct-completion evidence path; creators should write the matching boolean even though Spynel enforces the mode independently. In `skip-trivial`, choose `review_required` by the expected risk reduction versus review latency and cost. Use `true` for broad, high-risk, hard-to-reverse, security-sensitive, data/schema, infrastructure, deployment, release, migration, or materially uncertain work. Use `false` for read-only work and minor, localized, easily reversible changes with clear acceptance criteria and proportionate verification. Honor explicit user guidance for speed or no review unless material risk justifies review; when risk is genuinely uncertain, fail safe to `true`. Goal derivation, title, origin, duration, notifications, and incidental file changes never decide the value by themselves. The goal planner chooses per child task only in `skip-trivial`, while notification and mandatory goal-review policy remain independent.

The reviewed lifecycle is `todo -> working -> review -> reviewing -> done`. A valid direct-completion task may instead move `working -> done` only with a valid `completed` summary: `outcome` records what changed or was collected, required `evidence` records proportionate verification and the inspected boundary, required `uncertainty` records residual risk or what remains unknown, and `completed_at` exactly matches `updated_at` in UTC. Spynel returns an invalid direct completion to `todo` without terminal hooks or notification. In `skip-trivial`, a no-review task manually placed in `review` receives normal independent review. In `never`, queued review work returns to `todo` for a direct-evidence completion pass instead of starting a reviewer. Spynel alone claims queued files into `working` or `reviewing`. Reviewers start from independent assessment. When every finding is trivial, localized, low-risk, and within scope, they may correct it and rerun verification; nontrivial, broad, risky, uncertain, or design-dependent findings return the task to `todo` without reviewer implementation. Resolved waiting work returns to `todo`; an optional RFC 3339 `wake_at` lets Spynel do that automatically. When a safe low-risk fallback should be chosen after that time, record it explicitly in `## Progress`; omit `wake_at` when human judgment remains indispensable.

Optional `notify` front matter contains only `enabled`, stable `origin` (`telegram`, `whatsapp`, `tui`, or `cli` plus `/conversation`), and selected outcomes (`done`, `failed`, `waiting`, or `cancelled`). Goal-derived and other child tasks default to notifications disabled. Workspace `orchestrator.task_notifications` chooses `off`, `decide`, or `always`; notification agents act through supplied authorized CLI actions whose send boundary atomically journals a per-transition success receipt, while `decide` requires an explicit authorized decline action and provider prose or silence is ignored. A task reaching `done`, `failed`, or `cancelled` is a settled result for its goal round; `waiting` is not settled.

The optional `completion_summary` is bounded task completion/review evidence only; notification decisions do not inspect it and it never represents delivery or response state. It contains only `verdict`, `outcome`, `evidence`, `uncertainty`, `reviewed_at`, `completed_at`, and code-managed `rework_count` fields. Reviewers record an `accepted` or `rejected` task-specific summary with `reviewed_at`; direct no-review executors must record `completed` with required `evidence`, required `uncertainty`, and matching `completed_at`; other terminal executors use matching `waiting`, `failed`, or `cancelled` verdicts. Spynel calculates duration, attempt, review, and rework metrics. Missing or malformed summaries remain non-blocking presentation input except when they are the required evidence gate for direct no-review completion.

`## Progress` is the durable handoff log. Agents and Spynel append exact UTC entries for meaningful work, evidence, blockers, waiting reasons and fallbacks, recovery starts/outcomes, deterministic transition repairs, scheduled wakeups, successful proactive sends, and visible terminal notification failures. Post-terminal notification journaling changes no status and creates no notification loop. There is no separate notification-response, acknowledgement, or reminder lifecycle. User replies are ordinary chat context. Progress entries never expose recipients, provider message identifiers, or secrets.
