# Spynel Workspace DOX

This directory is durable state owned jointly by the user, Spynel, and dispatched agents.

## Contracts

- Markdown documents are the source of truth. Keep their body human-readable and front matter machine-readable.
- Spynel is a classic program with no AI in its core. It coordinates external AI/coding harnesses through one assistant-facing relationship and durable workflows; never describe Spynel itself as an agent, invent product capabilities, or treat “One human → one agent → infinite agents” as a literal resource guarantee.
- `.spynel/config.yaml` is the private user configuration for the workspace root one directory above this state directory. The `.spynel` location is fixed; no `workspace.state_dir` setting exists.
- Do not edit `.spynel/runtime/leases/`; Spynel owns processing leases and recovery bookkeeping.
- Do not edit or publish `.spynel/history/`, `.spynel/jobs/`, `.spynel/attachments/`, `whatsapp.db`, or harness session data; they may contain secrets, captured execution output, remote media, and private conversations.
- Automatically managed speech models live outside this workspace. Original voice attachments remain workspace-owned.
- Agent prompts under `.spynel/prompts/` are user-overridable workspace templates. Preserve local customizations during upgrades; keep project-specific guidance in the workspace root and nearer project `AGENTS.md` files.
- Standing workspace-owner behavior lives in exactly one Markdown file per role under `.spynel/instructions/`: `agent-chat.md`, `agent-developer.md`, `agent-reviewer.md`, `agent-notification.md`, and `agent-heartbeat.md`. Spynel validates and loads only the matching file fresh at the end of every relevant prompt. Current explicit requests and platform/system safety plus the nearest AGENTS.md/DOX contract take precedence. Preserve these files during upgrades; never store secrets, recipient identifiers, transcripts, one-off directions, or speculative preferences in them.
- The chat prompt runs a lightweight communication dispatcher. It answers questions and reports status, records one finite independently verifiable objective as a task, records long-lived or multi-round outcomes with measurable bars as goals, and leaves substantive execution to orchestrated document sessions. `/task` and `/goal` add the corresponding user-overridable creation directives to that same communication session; they are not deterministic file shortcuts. The dispatcher performs routine bounded inspection silently and returns exactly one brief, natural, outcome-first result with no preamble or progress messages for ordinary question, status, or delegation turns. Routine confirmations hide task/goal files, paths, IDs, metadata, lifecycle details, and orchestration mechanics; explicit technical-detail requests and dedicated status, job, task, goal, log, or document-inspection commands remain precise. Telegram and WhatsApp routine confirmations never contain local-path Markdown links.
- Authenticated workspace operators see the same global live and archived jobs and bounded task/goal inventories through Telegram, WhatsApp, TUI, CLI, and the shared application/API paths. Conversation identity, creation channel, and `notify.origin` are not inspection or control ACLs; notification origin remains outbound delivery metadata. Job archives are bounded redacted inspection data only and never workflow authority.
- Themes in `.spynel/themes/` are user-overridable semantic TUI palettes. Keep every required color and a unique safe name so Spynel can validate and switch them atomically.
- Extensions in `.spynel/extensions/` are trusted executable code. Review repositories before installing them.
- Spynel alone claims queued documents and owns phase leases/recovery. Agents record progress, update status and exact UTC timestamps, and move files only through allowed transitions without bypassing review or live ownership. Terminal and actionable unscheduled waiting task transitions directly dispatch one ordinary notification agent with the task and CLI guidance; that agent decides and edits the task log itself, while provider output has no framework meaning.
- The semantic heartbeat is a non-overlapping primary-owned worker. The framework ignores provider output and persists no heartbeat result, health, incident, escalation, or retry state; the agent uses ordinary Spynel CLI inspection and durable workflow contracts to make and journal evidence-backed repairs. Ordinary terminal and actionable unscheduled waiting task transitions dispatch the notification agent directly.
- Task front matter carries explicit boolean `review_required`; missing or malformed values fail safe to review under the default `harness.reviews: skip-trivial` mode. That mode chooses independent review when its expected risk reduction outweighs latency and cost: broad, high-risk, hard-to-reverse, security-sensitive, data/schema, infrastructure, deployment, release, migration, or materially uncertain work normally requires it, while read-only work and minor, localized, easily reversible changes with clear verification may complete directly. `always` forces all tasks through review and `never` forces all tasks through direct completion; Spynel enforces either override independently of front matter. Goal derivation alone never decides task policy in `skip-trivial`; planners choose per task. Direct completion records proportionate evidence and residual uncertainty. Goal planners define the success bar and create linked task rounds without implementing them, recording the exact current cohort in `round_task_ids`. Active goals carry no lease; after that cohort settles, a fresh goal-review session compares cumulative evidence to every criterion and either returns the goal to planning or moves it to `waiting`, `done`, or `abandoned`. Task review mode never bypasses goal outcome review, and task completion never directly completes a goal.
- Optional task notification metadata supplies only an authorized stable origin and supported outcome values; it never disables mandatory decision coverage, and transport secrets or unnecessary sender data never belong in task files.

## Structure

- `config.yaml` owns validated user configuration for the workspace.
- `tasks/` owns finite work items and their queue, claim, review, waiting, and terminal folders.
- `tasks/archive/` is cold retention history: cleanup alone moves old terminal tasks there unchanged, and ordinary dispatch, review, recovery, status, notification, and goal-settlement workflows exclude it.
- `goals/` owns proposed, planning, active, review, waiting, and terminal long-term outcomes.
- `prompts/` owns user-overridable channel, slash-command creation, task implementation/review, goal planning/review, recovery, notification, and semantic-heartbeat lead messages.
- `instructions/` owns persistent, workspace-scoped standing behavior for the five agent roles.
- `themes/` owns named semantic TUI and terminal-Markdown palettes.
- `extensions/` owns installed Git extensions and hook manifests.
- `history/` owns independent append-only histories per channel and conversation.
- `jobs/` owns private bounded job metadata, the atomic 1..9999 job-number sequence, and captured event output; private generation identities prevent reuse collisions.
- `attachments/` owns private TUI, Telegram, and WhatsApp media referenced from messages.
- `runtime/` owns Spynel leases, harness session mappings, and transient bounded work files.
