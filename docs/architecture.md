# Architecture

Spynel is a classic, non-AI program. Its architecture keeps deterministic communication, state, orchestration, and lifecycle management separate from the intelligence supplied by external coding harnesses. This boundary lets Spynel exploit improving harness capabilities instead of duplicating or competing with them.

| Boundary | Ownership |
| --- | --- |
| `agentdocs` | Curated offline topics, stable references, bounded pagination/search, versioned JSON, and shared help metadata. |
| `cli` | Interactive/server composition plus bounded non-visual automation commands and output contracts. |
| `core` | Transport-neutral messages, streamed events, form screens, controls, and slash-command metadata. |
| `config` | Typed defaults/validation, atomic private persistence, and newest-only live snapshots. |
| `app` | Shared commands, screen construction, configuration transactions, per-conversation dispatch, status, logs/jobs, durable-work listings, onboarding, and branching. |
| `channel` | TUI/Telegram/WhatsApp adapters plus isolated hot-reload supervision. |
| `harness` | Harness contract/capabilities, catalog and idle-only switching, Codex app-server, Claude Code print mode, Pi RPC, and shared ACP v1 stdio sessions. |
| `history` | Append-only JSONL, bounded reverse reads, discovery previews, clearing, and point-in-time branch copies. |
| `instructions` | Fixed-role validation and final prompt import for bounded workspace-owner standing instructions. |
| `instance` | Cross-platform primary-server election, lock-free atomic lease discovery, heartbeat renewal, and fenced stale takeover. |
| `localapi` | Authenticated loopback TUI/CLI-to-owner streaming, typed status, and bounded shared-state snapshots. |
| `media` | Private streamed attachment commits, validated outbound file directives, serialized Parakeet processing, and coordinated per-user managed speech models. |
| `markdown` | GitHub-flavored terminal rendering plus Telegram HTML and WhatsApp-native conversion. |
| `orchestrator` | Markdown claims, implementation/review phases, leases, semantic workflow audits, durable notification outbox, jobs, and stale recovery. |
| `startup` | Reversible workspace-specific systemd, launchd, and Task Scheduler registration. |
| `theme` | Validated semantic palettes loaded from workspace YAML with a built-in compatibility fallback. |
| `extensions` | Trusted Git installation and bounded executable-hook protocol. |
| `updater` | npm release discovery, bounded version checks, and retry-safe application-version migration hooks. |
| `workspace` | Embedded editable configuration, prompts, and DOX templates plus private directory creation. |

`cmd/spynel` is composition only. A channel translates external traffic into `core.Message` and calls the application; it never knows which coding-agent protocol is active. The application and orchestrator depend only on `harness.Harness`.

Persistent instructions form a narrow trusted-configuration boundary. Call sites select one compile-time role; repository data, task evidence, user messages, and model output never select a path. The loader accepts only the fixed `.spynel/instructions/agent-<role>.md` mapping, validates the complete regular UTF-8 file within 64 KiB, and returns no partial content on error. Workspace upgrade migrates legacy unprefixed names without clobbering canonical files and fails closed on content conflicts. App dispatch adds chat instructions after extension and review-mode prompt transformations; orchestration renderers add developer/reviewer, notification, or heartbeat instructions after their role-specific evidence and framework contracts. Harness-native prefixes are then prepended, leaving the persistent section at the logical end of the prompt.

`agentdocs` is intentionally below both `cli` and `app`. Its reviewed Go catalog contains no workspace or network readers. `spynel docs` therefore works before initialization and while disconnected, and its output cannot leak histories, leases, credentials, origins, or environment values. The concise `/help` index derives its stable topic labels from the same catalog while keeping channel-facing bodies short. Prompt renderers inject one absolute executable invocation for all supported harnesses and workflow phases. Live state remains behind typed application/status/job/task/goal/log boundaries rather than being copied into static documentation.

The typed status boundary joins process-local runtime counts to a bounded durable census of only the configured built-in task and goal routes; the task waiting-folder count is carried separately as a subset of active tasks. Folder state is authoritative for counting: active-folder Markdown remains counted when its front matter is corrupt or mismatched, while known task (`done`, `failed`, `cancelled`) and goal (`done`, `abandoned`) terminals are excluded. Unreadable folders or hard enumeration limits return lower-bound counts with rune-bounded, Unicode-control-free diagnostics. The primary-owned semantic scheduler publishes its actual next timer deadline under a mutex, marks an audit already in flight, and clears ownership before handoff completes; secondaries and offline one-shot services never infer a deadline from process start or configuration. The scheduler uses fixed delay rather than fixed cadence: it clears the deadline when an audit begins and arms the next exact production timer only after terminal provider release. Live changes to `orchestrator.enabled` or the semantic interval fence the prior scheduler term and cancel its audit context; an idle change resets the deadline from acceptance, while a change during an audit leaves the successor absent until completion and then uses the newest interval. Route cadence and parallelism remain restart-bound.

The durable-work list boundary extends that census into bounded item summaries for `/tasks` and `/goals`. It scans only configured built-in status folders, treats the folder as authoritative, refuses document symlinks, bounds directory entries, total documents, bytes, metadata, progress, diagnostics, and rendered items, and falls back to the safe file modification time when `updated_at` is invalid. The application layer defaults to all nonterminal work and applies deterministic recent, active, review, waiting, done, failed, and all semantic views plus day, limit, and detail options. The TUI, authorized Telegram/WhatsApp adapters, generic plain command API, and direct `spynel tasks`/`spynel goals` aliases all enter that same application boundary; CLI JSON wraps the terminal response in the shared NDJSON event schema. It sorts newest first and renders compact status/counter/latest-progress rows without starting a harness or exposing full paths and unknown front matter.

## Screen contract

A `core.Screen` is a transport-neutral form or action list rendered instead of chat. It may also provide named tabs plus an active index for wizard progress, while a control's optional `Section` inserts a labeled group rule before that control. A sectioned disclosure merges its clickable Show/Hide label into that rule instead of rendering a duplicate heading and button. The TUI preserves transcript/composer state while a screen is open. A child screen names its parent; the TUI snapshots and restores the parent's controls, unsaved edits, focus, disclosure state, and scroll position when the child completes or is escaped. Ctrl+C is a global surface exit: from any non-required screen or modal it drops the entire in-memory screen stack and returns directly to preserved chat; required setup exits the application. The TUI also owns a reusable centered modal primitive above `core.Screen`: while visible it captures other keyboard events, renders the underlying screen in place, and resolves one selected outcome before returning control. Dirty-exit confirmation for `/config`, `/telegram`, and `/whatsapp` offers Save through the ordinary validated persistence path, Discard without persistence, and safe-default Keep editing. Its semantic-muted control hints occupy the lower border, with rule segments as separators and a blank interior row above. Successful persistence restores chat; failure preserves the live form. Scalar form controls and text commands use the same `config.Setting` keys, so validation and persistence do not diverge between local and remote setup.

The `theme` boundary validates complete semantic color maps from `.spynel/themes` and supplies twelve stock palettes—six light and six dark, with two explicitly color-blind-friendly palettes in each group—when an upgraded workspace has no theme files. A stable stock-order registry keeps `spynel` and `hack-the-box` first and second, groups all six dark palettes before all six light palettes in their approved relative order, and sorts user palettes after stock entries. Stock metadata and measured luminance enforce the matrix; contrast tests cover ordinary and muted text, layered surfaces and selections, selected controls, status accents, borders, inline code on elevated surfaces, and fenced code on the page canvas. A collection regression computes mean CIE 1976 Lab distance across twelve meaningful semantic roles for every same-appearance pair, while accessible palettes additionally simulate severe protanopia and deuteranopia and require status separation. These checks support rather than replace identical-fixture PNG and contact-sheet review. Existing custom themes may omit the newer metadata. Renderers consume semantic values rather than palette literals, so the continuous main background, muted-user-accent upper/lower half-height ribbons, bordered composer/pickers, unframed chat/forms, layered controls, scrollbars, chat labels, errors, and terminal Markdown switch together. Fenced code uses the semantic `code` role in truecolor rather than Glamour's process-global Chroma registry, and each theme change rebinds the textarea's cached style pointer so code and placeholder colors cannot leak from a prior palette. The primary accent owns Spynel identity; `You` uses the user accent directly, while ribbons blend that accent evenly with the page background to reduce their visual weight without adding another palette role. Messages share that canvas instead of receiving individual background cards. The shared application persists theme names; the TUI alone owns temporary arrow-key preview state.

The TUI event loop has a 16 ms normal-operation target and a 100 ms stressed-fixture ceiling. It never performs theme discovery or pasted-file probing, copying, or syncing itself. One cancellable paste command owns that work at a time; up to eight later pastes wait in order, Ctrl-C cancels the active import and clears its queue, and further admission remains visible literal composer text instead of being dropped or spawning more workers. Enter waits until placeholder imports settle, so a path can never be dispatched before its private attachment copy is committed. Streaming Markdown likewise has one render in flight. Deltas received during it update a bounded, control-sanitized plain preview and coalesce viewport publication to at most 60 Hz; results are accepted only for the current width and theme and only when their source is still a prefix of the live stream. An accepted current result is reused until stream content, width, or theme changes, and a superseded result waits one publication interval before replacement so a continuous delta burst cannot create a formatter loop. Large transcript rerenders caused by resize, theme, or history changes use the same one-in-flight/stale-result pattern. This keeps typing, scrolling, resize, and cancellation independent of slow disk or Markdown work while preserving final content and ordering. Finalized transcript Markdown is cached incrementally, and spinner-only ticks reuse it. `Update` calls over 16 ms, theme/paste/render work over 100 ms, and paste-queue pressure are rate-limited to one report per five seconds and forwarded through the authenticated loopback API into the owner's structured runtime logger; diagnostics never write directly to the alternate-screen terminal or trigger on frames. The mixed-load regression fixture exercises that update path while bounded workers perform Markdown/layout, runtime logging, durable history appends, task transitions, notifications, and channel activity; it reports event-loop p95 latency, maximum UI/background queue depth, and peak/final goroutine counts and can emit the standard Go CPU, allocation, block, mutex, scheduler, and goroutine profiles.

The composer panel, textarea, and cursor use the same inner cell width. Its visible height follows the textarea's word-aware, grapheme-width rows on the update that creates or removes them, including the fresh cursor row reserved at an exact fit; Up/Down continues through wrapped rows and reaches the first/final insertion boundary without hiding the cursor. Reported terminal width is also a hard frame boundary: the viewport, textarea, ribbons, forms, and pickers never impose a wider synthetic minimum, and cosmetic horizontal insets yield before content on unusually narrow terminals so every emitted row fits while the cursor and any feasible composer border stay visible. Below the minimum full-canvas height, history and inline pickers yield their rows, the textarea adopts the remaining physical composer capacity, and its private viewport reanchors to the cursor-bearing tail in the same resize update; header, exact composer border, and footer remain inside the terminal. Composer growth reduces the history viewport by the same row count. If history is detached, its offset moves by that exact delta (and reverses on shrink) to preserve the reading anchor; legitimate tail-follow remains attached and recent manual upward scrolling still suppresses it for two seconds. Terminal resize, asynchronous Markdown completion, streaming, and notifications keep their separate anchor policies. User prose preserves repeated authored spaces and indentation, moves any fitting word or number intact to a fresh row, and hard-wraps only genuinely overwide tokens at grapheme boundaries. Spy streaming and finalized Markdown share one effective width and source-preserving renderer, so styling, role prefixes, padding, and the scrollbar are each accounted for once without synthetic punctuation or continuation spaces.

Terminal Markdown parses prose before adding render-only wrap hints. Ordinary letter-based ASCII-hyphen compounds that fit the effective row therefore move intact to the next row when necessary, while URLs, command flags, subtraction, list syntax, code, and Unicode dash characters retain their original semantics. Compounds wider than the effective row receive bounded hard-wrap opportunities, and every private hint is restored or removed before ANSI output; persisted history and copied source remain unchanged.

Initialization is a required screen because no application service exists before `.spynel/config.yaml`. The workspace root owns one fixed `.spynel` state directory, and configuration paths continue to resolve from that workspace root rather than from the nested file's directory. Loading a standard legacy root `spynel.yaml` atomically publishes the canonical file without `workspace.state_dir` and removes the legacy source; a custom legacy state path fails with explicit move guidance instead of silently splitting state. Once `workspace.Init` succeeds, the same process loads the new project. It enters the welcome/chat surface when any non-custom catalog harness is detected, otherwise it opens the coding-harness chooser first. Interactive `spynel init` follows the same path; `--no-start` is the explicit automation mode. Welcome, configuration, harness/model selection, WhatsApp QR pairing, and conversation browsing use the same screen machinery.

## Communication dispatch

The user-overridable `.spynel/prompts/chat.md` contract makes each channel session a responsive human-facing control plane rather than an execution worker. Questions and bounded status checks are answered in that session. Routine question, status, and delegation turns do not narrate bounded inspection or durable writes; each emits exactly one brief, natural, outcome-first result with no preamble or progress messages. Task confirmations normally just acknowledge that work is underway; goal confirmations summarize the intended outcome and say planning has begun. Internal files, local links, paths, IDs, metadata, verification plans, lifecycle details, and orchestration mechanics remain hidden unless the user explicitly requests them or invokes a dedicated diagnostic/inspection command. Telegram and WhatsApp never receive local-path Markdown links in routine confirmations; TUI and CLI links are likewise opt-in. Exact blockers, security implications, destructive effects, failures, and required user decisions remain visible. Finite, independently verifiable work is captured as a task, while recurring or multi-round outcomes with measurable bars are captured as goals. `/task` and `/goal` append the literal request through the user-overridable `create-task.md` or `create-goal.md` directive and dispatch the combined prompt through the same communication session; the agent, not the command switch, performs duplicate-aware framework-compliant creation. Every agent-authored durable timestamp is taken from the environment's current UTC clock, and scheduled review dates are computed from that observed value instead of an estimated current time.

Task execution and review use queue/claim pairs `todo -> working` and `review -> reviewing`. A successor queue waits for the predecessor lease on the same durable task to reconcile, preventing a fast filesystem move from launching review before execution ownership is released; recovery also preserves an already-created review lease rather than moving its claimed document underneath the reviewer. `harness.reviews` deterministically overlays strict boolean `review_required`: `skip-trivial` keeps the fail-safe document policy, `always` forces review, and `never` forces direct completion while returning queued reviews to `todo` for the required direct-evidence pass. Missing or malformed values still normalize conservatively and never grant a direct completion in `skip-trivial`. The creator or goal planner chooses by expected risk reduction versus review latency and cost only in that default mode; goal derivation alone does not force review. Broad, high-risk, hard-to-reverse, or materially uncertain work normally queues a fresh review, while read-only work and minor localized reversible changes may complete directly from `working` with proportionate verification, evidence, residual uncertainty, and a UTC completion time exactly matching `updated_at`. The reviewer begins independently, may correct and reverify only trivial localized low-risk findings, and returns broader or uncertain findings to `todo`. Direct completion never claims independent verification. Transition reconciliation applies the live global overlay before redirecting forbidden transitions and rejects same-thread self-review. Goal outcome review remains mandatory in every task-review mode. A selected terminal transition first persists retryable notification-agent state; persistence failure retains reconciliation ownership instead of losing the event. A bounded action job then runs outside the scan lock. The agent receives explicitly delimited untrusted task evidence and prepared fixed-origin `spynel notify` actions and invokes the stdin send action itself; provider prose is ignored and no JSON is parsed. The CLI binds its stable event key to that pending transition, revalidates task plus channel authorization, uses the durable outbox, and appends progress through Spynel's locked atomic Markdown updater. A persisted per-transition journal intent makes retries reuse the same safe message and timestamp, and only that event's completed receipt can settle it, so overlapping repeated outcomes cannot cross-credit generic progress text. If a task moves after enqueue, recovery locates its current status-folder path by durable task ID and the event's phase/attempt and repairs the journal without another provider turn; if a newer claim has superseded that attempt, the old event fails closed rather than writing into the newer transition. `decide` records no-send only through the authorized `--decline` action; provider success without send or decline remains retryable, as do provider and missing-action failures in `always`. No notification response or reminder lifecycle is created; user replies remain ordinary chat context. Each matching executable extension receives a stable completion event ID; reconciliation records a per-extension receipt only after successful exit and retries every unrecorded hook with that same ID. Because a crash or receipt failure can follow an externally visible hook effect, consumers persistently deduplicate by event ID and Spynel makes no exactly-once side-effect claim.

Goals use a separate state machine: `proposed -> planning -> active -> review -> reviewing`. Planning owns the success bar and creates one numbered batch of finite tasks carrying `goal_id` and `goal_round`; it freezes the batch as `round_task_ids` and does no implementation. `active` has no goal lease. The manager requires the declared IDs to match current-round task metadata and applies the exact trigger: cohort settlement for `all_round_tasks_settled`, checkpoint time for `scheduled`, or whichever occurs first for `all_round_tasks_settled_or_checkpoint`. Harness completion posts a coalesced scan event so task transitions reconsider the goal promptly; periodic scanning remains crash/recovery defense. New checkpoints require a rationale and settlement-only is the default. Once eligibility atomically queues `review`, the review claim is immediate; `next_review_at` remains readable as round history but is never reapplied as a queue delay. A fresh reviewer records evidence for every success criterion and chooses `done`, `waiting`, `abandoned`, or a new separately leased planning pass. A `done` move lacking the machine-readable matching review verdict is rejected back to `review`. Task results therefore inform the goal without ever completing it mechanically.

Proactive delivery is provider-neutral at the application/channel boundary. Every delivery carries its stable outbox event ID, every origin must name an existing durable conversation, and Telegram or WhatsApp authorization is reapplied. Remote histories record a private sending/sent ledger keyed by that ID; failed and interrupted pre-send attempts remain retryable and ledger controls are excluded from conversation rendering. WhatsApp maps the event ID to `SendRequestExtra.ID`, providing server-side retry deduplication. Telegram deliberately retains the HTTPS Bot API and at-least-once retry semantics: because Bot API `sendMessage` has no caller-supplied idempotency field, a process crash after Telegram accepts a message but before Spynel commits `sent` can cause a rare duplicate. This accepted transport limitation never suppresses an interrupted pre-send attempt. During a live TUI response, every later delta restarts idle-boundary consideration; only whitespace or token-safe prose punctuation may split the stream. Spynel durably acknowledges the exact character offset before rendering that split and holds terminal presentation behind an in-flight acknowledgement, so live and restored ordering agree. TUI and CLI delivery becomes an ordinary `Spy` assistant history entry.

The notification agent may include a question and choices directly in its one message, but Spynel does not turn that into a separate action request. The exact text is durable task progress, and the same proactive assistant message is ordinary conversation history. A later user reply is handled by the communication agent using that normal history; if it resolves the recorded waiting reason, the communication workflow updates and resumes the existing task through its standard lifecycle. The semantic heartbeat sees the current waiting reason plus newest progress, including prior notification text, and independently decides whether another proactive message is useful. There is no reply pairing, acknowledgement, reminder, escalation, cross-channel fallback, or notification-specific status surface.

A live TUI follows durable pending-notification records. During an active stream it reconsiders each short delta-idle boundary and accepts whitespace or punctuation only when the trailing prose token is complete and the current line is not an open heading, blockquote, list item, indented code block, URL, or inline Markdown construct. It first acknowledges the exact Unicode-character offset through the authenticated application service, then commits the corresponding response prefix and inserts the queued notifications; deltas received during that acknowledgement remain the next streaming segment. A transient acknowledgement failure retries without changing the display, and terminal events wait for the result. Durable history resolution uses the acknowledgement to reconstruct response-segment/notification/continued-response order after restart. Without a safe boundary, the notification follows the terminal response. Cancellation persists and renders streamed response text before the error and queued notifications rather than discarding it.

Natural-language follow-ups use the active conversation session. Codex and Pi steer through their native protocols. Claude writes another text user message to active streaming-JSON stdin when its permission mode needs no approval callback; its tool-capable text modes and every ACP adapter declare queue behavior. Before starting the next provider turn, the supervisor collapses adjacent queued chat entries into one prompt: it keeps the newest complete bounded-history snapshot and appends every exact raw message once in arrival order. Job controls are never merged because each has an independent validation/reservation boundary. Intermediate provider responses retain continuation markers, and only the last terminal final/error ends application and supervisor activity. The application converts emitter handoff and terminal completion into balanced main-agent activity events for the TUI and Telegram; WhatsApp retains its broader transport-local lifecycle through final delivery. Both remote transports deliver only the last terminal response, while the TUI keeps the streamed presentation.

Durable task and goal claims set `first_assigned_at` once, while a separate `provider_iterations` value is reserved immediately before each ordinary dispatch, recovery, native or queued control delivery, and guarded continuation. Claims, runtime status moves, and reservations serialize on one cross-process lock stored above the sibling status directories, so its identity does not change when the document moves. A provider agent necessarily performs its own terminal status move outside that advisory lock; if such a move crosses reservation's atomic replacement, Spynel merges only the reserved timing into the moved document and removes the recreated stale source before provider delivery. Phase-specific attempt counters remain lifecycle metadata. Process-local jobs accept only non-regressing durable timing observations, so `/jobs` and `/job info` retain total lifetime/count across phase sessions, owner recovery, and replacement numeric job IDs. Their presentation maps `provider_iterations` to cumulative `N▶`; task jobs separately snapshot the durable implementation `attempt` as optional `M↻`, while goals and live or legacy jobs without that value omit `↻`. Legacy documents acquire timing only on their next real claim or provider reservation; corrupt or future assignment timestamps are repaired conservatively at that boundary.

Job controls are a non-owning path through that same harness supervisor. `/job message` wraps operator text as delimited untrusted coordination data and `/job ping` requests a durable semantic progress entry at the next safe opportunity; neither installs the command response as the provider emitter. Codex uses native steering, while Claude Code and future harnesses follow their declared native-steer or ordered same-session queue mode. For native steering, the adapter—not the supervisor—runs the durable provider-iteration reservation callback after it has fenced turn completion and immediately before delivery. A turn found inactive is rejected without reservation; once reservation succeeds, the adapter commits that control to the fenced provider delivery path. Definitive pre-delivery failures remain retryable, while an ambiguous transport error remains deduplicated. The supervisor caps each job queue at eight entries and deduplicates identical caller/job/control retries for one minute. On a terminal provider event attributable to a control, it may start one continuation only after the orchestrator revalidates the exact process owner, session, phase, lease, still-present claimed document, and nonterminal durable status. Cancellation, file movement, owner/session replacement, or a second terminal event disables continuation and leaves normal reconciliation/recovery authoritative. Control acceptance never advances durable state, and progress pings do not create heartbeat activity unless the live provider produces an event.

The plain CLI is another adapter over this control plane. `send`/`message` uses an independent named `cli` conversation and prints the last assistant-message item by default, every response delta with `--stream`, or complete NDJSON events with `--json`; durable history keeps the aggregate turn in every mode. If an elected workspace owner exists, the command routes through its authenticated loopback API so it sees the live harness, jobs, logs, and active turn; otherwise it creates a one-shot service without starting continuous orchestration. `followup` additionally sets a transport-neutral strict-active flag, which the service checks before writing history. Typed status and bounded conversation list/show/branch operations avoid scraping Markdown replies. Non-visual framework commands still pass through the shared slash-command handler, so configuration, task management, jobs, logs, stopping, and extension hooks retain channel-identical behavior.

## Harness lifecycle

The harness supervisor owns at most one running harness and exposes readiness without preventing the rest of Spynel from starting. A missing selection or executable can be recorded for setup when no harness is running. Reconfiguration constructs a replacement before swapping a working harness and refuses to switch while the current harness has active work.

Codex starts one `codex app-server --stdio` process, performs the initialize handshake, and maps stable Spynel session keys to persisted thread IDs. An idle message uses `turn/start`; a message arriving during an active turn uses `turn/steer`; `/stop` uses `turn/interrupt` for that conversation only. `model/list` supplies its model catalog.

Claude Code starts one bounded print-mode process per turn with stream-JSON/partial output. Read-only plan mode and non-privileged unrestricted bypass also use streaming JSON input, so a follow-up written before the result remains in-process guidance; Spynel closes stdin after the result and waits for process exit. Workspace-write uses ordinary text input with accept-edits and shell permission. Because Claude refuses bypass under root/sudo, privileged unrestricted mode likewise uses text input with accept-edits plus an all-tools allow rule and emits a runtime warning. Those text-input modes declare queue behavior, so follow-ups resume the same stored session in the next process. The process is interruptible, documented model aliases form the selector catalog, and exact configured identifiers are preserved. These are Claude-native permissions, not OS sandboxing.

Pi starts one long-lived `pi --mode rpc` JSONL process per active conversation, persists its session file, and uses `steer`/`abort` for active-turn guidance and cancellation. Responses are terminal only at `agent_settled`; `agent_end` may precede retry, compaction, or queued continuation. Read-only mode limits Pi's enabled tools to read/search primitives. Pi RPC has no stronger native sandbox boundary.

ACP starts the selected alias or custom command once and negotiates stable protocol version 1 over newline-delimited JSON-RPC stdio. Each conversation receives an independent `session/new`, then restart recovery prefers advertised `session/resume` and falls back to `session/load` or a new session. `session/update` streams agent text/tool status, `session/prompt` supplies the terminal stop reason, and `/stop` sends `session/cancel`. Model and thought overrides use advertised session config options. Spynel advertises no client filesystem or terminal callbacks and automatically resolves permission requests according to the selected sandbox; an agent that acts without requesting permission remains trusted local code. ACP v1 exposes no in-flight prompt steering, so all ACP profiles use the batched same-session queue.

Stable session keys include:

- `chat:tui:local-<instance-id>` for every running window and `chat:tui:<branch>` after resume; legacy `tui/local` history remains available to branch through `/resume`;
- `chat:telegram:TG-<user-id>` and `chat:telegram:TG-group-<chat-id>`;
- `chat:whatsapp:WA-<number>` and `chat:whatsapp:WA-group-<group-id>`;
- `orchestrator:<route>:<phase>:<document-id>:<attempt>` for task implementation/review and goal planning/review.

Every harness profile uses a separate private session map. Claude, Pi, and ACP records include a non-secret runtime-policy identity; a changed policy starts a fresh provider session rather than replaying stale permission decisions. Pi stores its provider session-file path, while ACP stores only the opaque session ID. Bounded Spynel history remains the prompt-context fallback. `/clear` first resets the inactive mapping, then clears history; if reset fails, history is preserved. `/new` resets only the harness session and leaves history intact.

## Channel lifecycle

The channel supervisor consumes only the newest persisted settings snapshot. A fingerprint change revokes the stale channel's runtime authorization before cancellation and starts a replacement; disabling revokes first and publishes an unconfigured state. Allow-list-aware adapters expose a side-effect-free preflight that runs before the supervisor publishes `connecting`. Invalid authorization is retained as a connection error for that fingerprint, and the first observed live authorization loss wakes the adapter's active run loop so Telegram closes its poll/webhook transport and WhatsApp disconnects; the five-second reconciliation tick does not create a reconnect storm. Telegram permits one teardown-only provider action after revocation—`deleteWebhook`—so shutdown cannot leave a dead local listener registered, while all delivery and other provider calls remain blocked. Other build/start failures remain retryable and become connection errors plus runtime logs. No failed bot is allowed to terminate the TUI or task manager. Telegram and WhatsApp also receive live settings resolvers and repeat canonical allow-list validation at each inbound and outbound security boundary; constructor snapshots, identity mappings, session databases, group addressing, and prior event authorization are never sufficient.

Telegram and WhatsApp each use a bounded incoming queue. External media streams directly into a private temporary file with a byte cap, fsyncs, and becomes visible through a collision-safe commit only after success. Voice transcription uses one shared serial token and a cached sherpa-onnx Parakeet recognizer. Miniaudio converts WAV/FLAC/MP3, while a checksummed and packet-bounded Ogg reader feeds Opus voice packets to an in-process pure-Go decoder; both produce bounded mono 16 kHz PCM chunks. Composition resolves `spynel/speech/v1/parakeet` below the OS per-user cache once and injects it into media. A cross-process file lock protects validation, safe legacy copying, checksum-pinned private downloads, and atomic version publication; original attachments and other transient channel state remain workspace-owned.

## Process lifecycle

All `serve`/TUI processes rooted at the same state directory participate in one server election. A short-held cross-platform OS file lock serializes each read-check-write decision for `.spynel/runtime/primary.json`; the owner record includes a random process instance ID, PID, loopback endpoint, per-term bearer token, start time, and heartbeat. The owner renews every five seconds. Other processes check once per second and may replace it only after the heartbeat is 30 seconds old. Renewal and release verify both instance ID and term token, so a stalled former owner cannot overwrite or remove the winner when it resumes. An idle local TUI can request `/primary`: the owner stops all owner-only loops before writing a fenced reservation, the named requester can acquire immediately, other contenders remain excluded, and the reservation opens to fallback takeover after ten seconds if the target disappears.

The elected owner alone constructs the application service and starts Telegram, WhatsApp, and continuous Markdown orchestration. Every TUI—including the owner's—and transient plain CLI clients use the authenticated loopback API for message/event streaming; TUI clients additionally use screen actions/settings and poll bounded shared state, while CLI clients request typed status on demand. Long message streams and `run-once` calls use their caller context rather than a fixed response-header timeout because provider work may legitimately take minutes. This keeps harness session persistence and mutable runtime state single-writer. A process records whether a healthy owner existed before joining the election: an initially ownerless winner resumes the latest disk-backed TUI conversation and harness session, while a process that found an owner or lost the initial race starts a unique empty conversation with the welcome banner. A secondary reloads `.spynel/config.yaml` before promotion and keeps its existing conversation identity when ownership changes.

`/restart` is dispatched by the shared application service on every channel. The service persists and emits its final acknowledgment before publishing a coalesced process request. The CLI gives the TUI enough time to render that event, cancels the server context, closes the harness, restores the terminal, and relaunches the current executable with the active server arguments and working directory. Unix replaces the process in place so service-manager identity is preserved; Windows starts the successor with inherited standard streams before the old process exits. A TUI entered through `spynel init` restarts as the equivalent `spynel serve --tui --config <initialized-file>` invocation instead of trying to initialize the existing workspace again.

The npm launcher identifies its package root to the Go runtime. Interactive TUI starts query npm's `latest` endpoint with a ten-second total deadline and may prompt for `npm update`; noninteractive commands and generated `--automatic-startup` login services skip that proactive path. Explicit `/update` checks share the same deadline. `/update install` persists its acknowledgment and stops the owner with a dedicated exit code plus the normalized restart arguments (including the `init`-to-`serve --tui` continuation). The supervising Node process then runs the appropriate local/global npm update while no Go executable is mapped, which avoids Windows replacement failures, and launches the new binary. Every semantic application version is recorded per workspace. On a transition, trusted `update.before`, compiled-in migrations, and `update.after` receive the exact old/new versions; the recorded version advances only after all hooks succeed.

## History and memory

Each channel/conversation has an independent append-only JSONL file. Harness context reads backward in 64 KiB blocks and stops at both the configured message and character limits. Oversized single records are bounded rather than forcing the complete file into memory.

Each TUI startup and live display is a 500-entry/500,000-rune tail with an explicit omission notice. The first election winner in an ownerless workspace selects the latest TUI history; additional live windows use `tui/local-<instance-id>`, preventing histories or communication harness threads from colliding. A window keeps its selected identity when its process gains or loses ownership; legacy `tui/local` can be selected by ownerless startup and remains discoverable through `/resume`. `/resume` scans filenames, reads at most one newest entry for each preview, and returns at most 100 choices. Selecting one captures the source size under its conversation lock, then streams exactly that point-in-time prefix to a new random eight-character TUI branch. The plain `conversations resume` command uses the same copy contract but targets a new `cli/resume-<short-id>` branch. Only bounded display/query tails are loaded; the complete copied JSONL remains on disk. Remote channels continue using their stable histories and are never rewound.

Operational logs pass through an attributed application boundary that removes controls, redacts common credential forms, and bounds entries before appending private per-session JSONL under `.spynel/runtime/logs`. Harness, extension, media, channel, orchestration, job, configuration, and top-level command failures use that boundary. Subprocess diagnostics are bounded and captured while intentional JSON protocol stdout, CLI response output, and user content remain on their dedicated streams and are not logged. In particular, startup registration helpers and extension Git installation retain separately attributed stdout/stderr plus exit status, cap each stream at 64 KiB, and omit command arguments so repository URLs or scheduler actions cannot become log metadata. The application chronologically merges overlapping session files into a newest-4,096-entry view with deterministic source-file and record-position tie-breaking, ignores corrupt or partial records, rotates at 2 MiB with eight-file retention, and treats persistence failure as non-fatal. Restore, append, clear, and close failures create non-recursive in-memory diagnostics so `/log` exposes when durable crash evidence is unavailable. Errors and clean session boundaries are synced where feasible; `SIGKILL`, power loss, and diagnostics emitted directly by native libraries below Go's writers remain unable to guarantee a final captured record. Runtime updates use newest-only channels. Jobs contain one mutex-protected canonical snapshot with structured live execution state, bounded detail/activity/reconnect/recovery fields and, for orchestrator work, the route and linked durable filename. Provider adapters publish lifecycle signals rather than making `/jobs` parse prose; Claude Code's transport-only reconnect diagnostic is handled by one anchored adapter mapping. Lease states map into the same live vocabulary while their exact values and workflow phase remain available to `/job info`; durable document outcomes stay separate. Late events address a never-reused numeric job ID and cannot revive or mutate a finished/newer execution. Detailed job inspection joins that snapshot to the current persisted lease and Markdown document, reads at most 2 MiB, exposes an explicit metadata allowlist, sanitizes controls and Markdown metacharacters, bounds rendered progress to three newest entries and 900 runes total, then rechecks process-local liveness to tolerate concurrent completion. It never reads harness transcripts or emits full session keys. Audio input, models, attachments, complete conversations, and obsolete harness output are disk-backed instead of retained as application state.

Routine informational persistence uses a bounded non-blocking worker; error, fatal, partial-tail, and session-boundary records use acknowledged flushes. Queue admission, acknowledgements, control operations, shutdown, and directory-lock acquisition have a two-second bound, after which Spynel continues with the in-memory view and a persistence diagnostic. The runtime serializes append admission with clear so a record accepted before `/log clear` cannot reappear after restart. A directory-scoped operating-system lock serializes rotation across processes without allowing a lock holder to stall startup indefinitely, and each active session file remains locked for its open lifetime so retention never unlinks another process's evidence. Owned goroutine boundaries and the configured CLI process boundary retain panic stacks before preserving panic semantics; a panic before any workspace configuration can be resolved has no safe durable destination and remains terminal-only.

## Configuration transactions

Commands and forms clone the current config, parse every change, validate the complete result, and atomically persist it. The public harness contract contains `name`, `model`, and `sandbox`, plus `acp_command`/`acp_args` only for the explicit custom ACP profile. Built-in commands, working directory, approval policy, network flag, and effort are derived during composition; arguments never pass through a shell. Sandbox values are normalized to the closest provider protocol with unrestricted access as the default. Harness changes are staged before persistence. Startup registration is applied after persistence but rolls YAML and the staged harness back if the OS operation fails. Secret values never enter replies, status, or durable command history.

## Orchestration durability

For every built-in processing phase, Spynel writes a `claiming` lease with source, target, and manager-owner identity before atomically renaming the queued Markdown file into `working`, `planning`, or `reviewing`. It then updates front matter and marks the lease `processing`. The in-memory in-flight map prevents duplicate goroutines; the durable lease and claimed path prevent duplicate work across restarts. A newly elected manager immediately recovers claims owned by its predecessor, while same-owner stale timeouts still protect known-live sessions. Startup can finish a journaled claim or synthesize a recovery lease for a claimed file that lost its lease between filesystem operations. Task implementation/review, goal planning/review, creation, and recovery prompts explicitly start their DOX walk at the hidden `.spynel/AGENTS.md` and continue through the claimed route, so an agent cannot mistake a dot-directory-skipping search for an instruction-free workspace.

Every harness event refreshes the heartbeat. A completed harness turn does not remove the lease by itself, because the agent still owns the durable file transition. If a claimed file remains beyond `stale_after`, Spynel resumes its phase with the recovery prompt, except while that exact harness session is still active in the current owner process. An unleased claimed file is recovered immediately after owner election. Recovery starts, deterministic transition redirects, due waiting wakeups, automatic goal-review queues, accepted semantic-repair findings, and queued proactive notification text append exact-UTC entries inside the affected document's `## Progress`. A semantic repair does not enter recovery until its progress entry succeeds. Due waiting tasks return to `todo`; due goals return to their recorded planning or review phase. Completion is therefore based on explicit filesystem state, not optimistic interpretation of chat text, without blindly duplicating partially applied work. Recovery may select another configured outcome allowed for its owned phase when normal order is a proven dead end, but cannot bypass review, live ownership, or destructive-safety checks and must journal the evidence and exception.

## Extension direction

New built-in transports implement `channel.Channel`. New coding agents add one catalog/factory entry, implement `harness.Harness`, and explicitly declare native steering or queue behavior. ACP-compatible agents normally need only a command/argument alias around the shared adapter; other adapters own their protocol translation. Queue-mode chat bursts are batched automatically. Project extensions remain executable hooks with JSON stdin/stdout so they are portable across languages and Go versions. They are intentionally trusted code rather than a misleading partial sandbox.
