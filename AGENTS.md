# DOX framework

- DOX is the AGENTS.md hierarchy used by this project.
- Agents must follow the applicable AGENTS.md chain before editing files.

## Core Contract

- AGENTS.md files are binding work contracts for their subtrees.
- Durable docs, source files, prompts, tests, and packaging metadata must stay understandable from the nearest applicable AGENTS.md plus every parent AGENTS.md above it.
- Spynel is the Go application rooted in this repository. It owns chat transports, harness sessions, deterministic markdown orchestration, persisted runtime state, executable project extensions, documentation, and distribution.
- Describe Spynel consistently as a classic, non-AI program that coordinates and oversees external AI/coding harnesses. It is not itself an agent and does not compete with or duplicate harness intelligence. The product relationship is one human through one assistant-facing relationship to many agents; “One human → one agent → infinite agents” is a conceptual expression of scalable leverage, never a literal resource guarantee. Use “Simplicity at scale.” as the primary slogan and “Simplicity. Leverage. Quality.” as the defining words. Do not invent capabilities, integrations, guarantees, or adoption claims when adapting this positioning to public copy.
- The retired Python prototype and the former nested Go layout are not part of the repository. Product behavior, tests, documentation, packaging, and automation use root-relative paths.
- Produce one cross-platform application that hosts the styled TUI, long-running communication channels, coding-harness sessions, Markdown orchestration, and project extensions. Release archives include the sherpa-onnx native runtime beside the executable.
- `cmd/spynel` is composition only. Channels translate external messages into the provider-neutral application contract and never call a coding harness directly.
- Every channel conversation and orchestrated Markdown file has an independent harness session. Persisted leases prevent duplicate orchestration and recover stale work across restarts.
- Accepted human conversation messages carry private stable source identities and append-only execution/admission/terminal/cancellation correlation. The default-on live `orchestrator.retrigger_unresponded_messages` feature is owned only by the elected primary, coalesces startup/reconnect signals with a five-minute bounded 24-hour scan, fences its final reservation through provider admission under the exact election term, and uses the ordinary same-conversation communication session with relevance-first guidance and a visible handled-or-skipped response, including live local TUI transcript delivery. First upgrade creates a forward activation baseline without inspecting, inferring, backfilling, or replaying legacy history; missing or pre-activation correlation is categorically ineligible. Exact handled, active/queued, durable task/goal-linked, cancelled, prior-recovery, unauthorized, group, corrupt, and overflow cases suppress or fail closed without partial-tail dispatch. This is terminal-result recovery, not notification delivery or generated-reply redelivery; public logs/status expose aggregates only.
- Every running process in one workspace participates in a single primary-server election. The owner alone runs Telegram, WhatsApp, and continuous Markdown orchestration; every TUI reaches the owner's application service over an authenticated loopback API. Primary leases carry a non-secret digest of a private per-user/per-environment installation token so a client rejects a known-foreign host/container loopback before dialing; missing or invalid identifiers remain fresh-owner fenced and receive only bounded compatibility readiness. Interactive secondary TUI startup reports connection progress before entering the alternate screen, while automation remains quiet. The first TUI in an ownerless workspace resumes the latest TUI communication session, while additional live TUIs receive independent sessions. Five-second heartbeats, a 30-second stale threshold, lock-free discovery of atomically published leases, serialized compare-and-replace takeover, and target-fenced `/primary` handoffs prevent duplicate owners while allowing secondary startup, explicit promotion, or recovery from a dead or stalled server.
- The main communication agent is a responsive dispatcher: it answers questions and reports durable state, routes finite work into tasks and long-term objectives into goals, and leaves substantive execution to independent orchestrator sessions.
- The communication agent performs bounded inspection without narrating routine tool steps, then gives one brief, natural, outcome-first result. Ordinary question, status, and delegation turns have no preamble or progress messages. Routine task and goal confirmations hide internal files, paths, IDs, metadata, lifecycle details, and orchestration mechanics; explicit detail requests and dedicated diagnostic commands such as `/status`, `/jobs`, `/tasks`, and `/goals` remain technically precise. Telegram and WhatsApp routine confirmations never contain local-path Markdown links. Agents must obtain current UTC from the environment instead of estimating timestamps written into durable Markdown state.
- The communication agent carries a framework-owned evidence-grounded honesty contract even when a workspace preserves a customized chat template. It must distinguish observation and durable or source-backed evidence from inference, uncertainty, and unknowns; never lie, fabricate evidence, invent causality, imply inspection it did not perform, or present stale or unverified claims as facts; and verify materially uncertain current, workspace-specific, causal, high-impact, completion, dispatch, delivery, release, external-state, or code-behavior claims when bounded authoritative inspection is practical. Otherwise it says that it does not know yet and offers or dispatches investigation. Corrections identify the unsupported claim and changed evidence rather than reflexively agreeing. Stable low-risk knowledge remains responsive without ritual lookup, and this behavioral contract is not represented as a mathematical guarantee of model perfection.
- Runtime state, histories, WhatsApp credentials, installed extensions, and the canonical user configuration `.spynel/config.yaml` belong inside each initialized workspace's fixed `.spynel/` directory. Relative configuration paths resolve from the workspace root, and no configurable state-directory key exists. Automatically managed speech models are the exception: they live in the operating system's per-user cache under Spynel's versioned speech namespace and are shared across compatible workspaces for that user.
- Spynel is alpha software and supports only its current configuration, state, manifest, session, and workflow schemas. Reject obsolete fields, names, aliases, and layouts explicitly; do not retain compatibility migrations, fallback readers, or retired fixtures. Prefer one clear current representation over preserving pre-release data.
- There is no OpenAI-compatible HTTP façade. Channels, harnesses, and trusted executable hooks are extended through explicit interfaces.

## Read Before Editing

1. Read the root AGENTS.md.
2. Identify every file or folder you expect to touch.
3. Walk from the repository root to each target path.
4. Read every AGENTS.md found along each route.
5. If a parent AGENTS.md lists a child AGENTS.md whose scope contains the path, read that child and continue from there.
6. Use the nearest AGENTS.md as the local contract and parent docs for repo-wide rules.
7. If docs conflict, the closer doc controls local work details, but no child doc may weaken DOX.

Do not rely on memory. Re-read the applicable DOX chain in the current session before editing.

## Update After Editing

Every meaningful change requires a DOX pass before the task is done.

Update the closest owning AGENTS.md when a change affects:

- purpose, scope, ownership, or responsibilities
- durable structure, contracts, workflows, or operating rules
- required inputs, outputs, permissions, constraints, side effects, or artifacts
- user preferences about behavior, communication, process, organization, or quality
- AGENTS.md creation, deletion, move, rename, or index contents

Update parent docs when parent-level structure, ownership, workflow, or child index changes. Update child docs when parent changes alter local rules. Remove stale or contradictory text immediately.

## Project Contracts

- The canonical repository and Go module path is `github.com/agent0ai/spynel`; release, package, issue, and documentation links use that owner and repository.
- Keep the root README's public community links aligned with the Agent Zero ecosystem: the Agent Zero website and repository, Discord, X, YouTube, GitHub Sponsors, and Spynel's own GitHub Issues page. Do not add product-specific links or unsupported Spynel services.
- Keep application and orchestration code harness-neutral. Codex, Claude Code, Agent Zero CLI, Pi RPC, and ACP behavior belongs in `internal/harness`; future harnesses register metadata/factories there, implement the same interface, and explicitly declare native-steer or queued follow-up behavior. ACP-compatible CLIs normally use one concise command/argument alias around the shared v1 stdio adapter; only the explicit custom ACP profile accepts a user command and shell-free argument list. Agent Zero CLI uses `a0 acp` and must pass `a0 acp --check` before discovery reports it as available.
- Keep every harness scalar under `.spynel/config.yaml`'s `harness` section and require exact current catalog names and sandbox/review values after case/edge-whitespace normalization. All one-line live agent prefixes default empty. Optional harness-native commands such as `/goal` are outer-trimmed and separated from the original prompt by exactly one ASCII space immediately before dispatch; empty or whitespace-only prefixes preserve the prompt byte-for-byte. `harness.reviews` overlays task policy with `skip-trivial` (default agent-decided behavior), `always`, or `never`; enforce `always`/`never` independently of task front matter and prompt overrides, while mandatory goal outcome review remains separate.
- Keep all exposed non-extension settings live behind the shared save-and-reload boundary. The only restart-bound settings are `extensions.enabled`, `extensions.directory`, and `extensions.hook_timeout`. A validated save atomically replaces canonical YAML, reloads that file into the shared process snapshot before returning, and publishes the refreshed snapshot to runtime owners; use minimal direct hooks only for owners that cache derived state. Model selection commits under the same fence as harness dispatch admission: admitted turns retain their captured model, including active native steering, while every provider dispatch snapshot ordered after the commit uses the new model, including queued continuations. Harness implementation, command, arguments, and sandbox changes remain transactional and idle-only. Subsequent operations read the refreshed snapshot, while active channels and in-flight orchestration may finish under their admitted state. Bare `spynel` deterministically launches the TUI; `spynel serve` is headless unless `--tui`, and the retired `channels.tui.enabled` input is normalized away rather than retained.
- The default CLI command is `spynel`; the project configuration file is `.spynel/config.yaml`.
- Keep the plain CLI equivalent to the non-visual application control plane: named disk-backed conversations, bounded streaming/NDJSON message input, active-turn follow-ups, structured status, conversation inspection/branching, attachments, shared slash commands, and trusted extension hooks must use the same application service as interactive channels.
- Authenticated workspace operators see one global live and archived job, task, and goal set through Telegram, WhatsApp, TUI, CLI, and the shared application/API boundary. Assign jobs workspace-local durable numbers from 1 through 9999, wrap to 1, and preserve a job's number through recovery and archival. Numeric lookup selects the newest generation after reuse; collision-proof archive identities remain private. Workspace-local job archives retain bounded redacted event streams through the chat-history retention boundary; they are inspection-only and never workflow evidence. Conversation identity, creation channel, and durable `notify.origin` are delivery metadata, never inspection or control ACLs. Preserve transport and loopback authentication before the shared handler, prevent cross-workspace archive reads, and expose only bounded privacy-safe projections without conversation IDs, prompts, session keys, notification origins, or arbitrary durable fields.
- Keep `spynel docs` as a separate harness-free, server-free interface over curated compiled documentation. Stable topic/section references, deterministic bounded text/JSON output, concise `/help` metadata, prompt guidance, and repository documentation must be validated together; static docs never read or impersonate live workspace state.
- Markdown task and goal files are the durable source of state. Front matter is machine-readable; bodies and agent logs are human-readable. Tasks are single finite objectives carrying explicit boolean `review_required`; missing or malformed values fail safe to review. Choose review by expected risk reduction versus latency and cost: broad, high-risk, hard-to-reverse, security-sensitive, data/schema, infrastructure, deployment, release, migration, or materially uncertain work normally follows `todo -> working -> review -> reviewing -> done`, while read-only work and minor localized reversible changes may use `working -> done` with proportionate verification, evidence, residual uncertainty, and an exact UTC timestamp. Explicit speed or no-review guidance is honored unless material risk justifies review. Goal derivation alone never forces task review; planners choose per child task, while independent goal review remains mandatory. Goals are measurable long-term outcomes following leased planning, passive task-round execution, and independent leased review; settled tasks are evidence rather than automatic goal completion. Every claimed phase has a persisted lease and orphan/stale recovery. Task reviewers may correct and reverify only trivial localized low-risk findings; broader or uncertain findings return the same task to `todo` for implementation. A recovery agent may choose another configured outcome allowed for its owned phase when evidence proves normal order would preserve a dead end, but it must journal the condition, evidence, exception, safety boundary, and next action and may never bypass required review, live ownership, or destructive-safety constraints. Spynel journals accepted heartbeat repairs, recovery starts, deterministic corrections, scheduled wakeups, and proactive-notification outcomes in `## Progress`. Every task transition to `done`, `failed`, or `cancelled`, plus actionable unscheduled `waiting`, directly starts one ordinary asynchronous notification-agent turn with the task and ordinary notification CLI guidance. The agent alone decides whether to send and directly records its send, skip, or CLI failure in task progress. Spynel does not persist notification-agent control state, interpret provider output, write a notification result, or recover/replay the turn. Ordinary channel authorization and delivery behavior remain unchanged. Executable hooks are delivered at least once with a stable `event_id`; persist successful per-extension receipts, retry unrecorded hooks with that ID, require consumers to persistently deduplicate visible effects, and never claim exactly-once arbitrary side effects. Bounded completion summaries distinguish ordinary direct completion from independently reviewed acceptance without acting as notification-delivery state.
- Shared `/tasks` and `/goals` commands inspect bounded durable Markdown state without invoking a harness. The identical contract is available through direct `spynel tasks`/`spynel goals` automation commands, the generic plain command API, the TUI, and authorized Telegram/WhatsApp messages. Bare commands default to all nonterminal work; `recent` uses `updated_at` windows of three and seven days respectively, while `active`, `review`, `waiting`, `done`, `failed`, and `all` provide semantic lifecycle views. Custom-day, bounded-limit, detail, and plain-CLI NDJSON options remain compact, newest-first, and explicit about unreadable or invalid documents.
- Runtime prompt templates ship in the package and are copied into initialized workspaces so users can override them.
- Every agent prompt receives one framework-owned scope-discipline rule after template rendering and before workspace-owner instructions, so stock and customized templates equally prioritize the smallest useful actions and verification. Developer and reviewer orchestration prompts additionally receive concise role-specific 80/20 guidance: implement the smallest maintainable solution for observed and realistic needs, and review practical correctness without demanding speculative completeness while flagging harmful overengineering. These rules never weaken explicit requirements or evidence-backed correctness, safety, authorization, privacy, destructive-action, data-integrity, lifecycle, independent-review, or data-handling contracts. Communication prompts additionally receive the evidence-grounded honesty contract through framework composition so ordinary saved preferences cannot remove it.
- Exactly five workspace-owner persistent instruction files live under `.spynel/instructions/` as `agent-chat.md`, `agent-developer.md`, `agent-reviewer.md`, `agent-notification.md`, and `agent-heartbeat.md`. Each matching file is validated and loaded fresh as the final separated prompt section; initialization and upgrade create only missing canonical files without replacing edits, and explicit current instructions plus applicable safety and AGENTS/DOX contracts take precedence.
- The elected primary alone schedules the semantic workflow heartbeat. Its enabled state and interval apply live, scheduling is fixed-delay, and one stable provider-neutral harness session remains non-overlapping and inspectable until provider release. The framework only triggers the worker and supplies minimal primitives; agents do the work. The heartbeat agent inspects bounded durable workflow state, decides from task progress whether a user wait has been inactive long enough and a reminder is useful, uses the ordinary recent-authorized notification CLI when appropriate, and records its send/skip/failure in that task's progress. Never implement this policy as classic-runtime reminder queues, waits, timers, thresholds, eligibility logic, identity linking, correlation, acknowledgement, deduplication, retry contingencies, or reminder orchestration. Ordinary terminal and actionable unscheduled waiting transitions still start the dedicated notification agent directly.
- Heartbeat and notification agents use one ordinary asynchronous job lifecycle. A successful harness `Send` is provider admission, not completion; keep the job and bounded context live through the first non-continuing terminal final/error event, cancellation, or timeout, archive every accepted event through that boundary, and settle ownership exactly once. `Codex turn started` is nonterminal. Late/duplicate terminal events are ignored, while heartbeat cadence/non-overlap remains separately fenced until provider release. Before task-notification dispatch, validate the task's enabled metadata and selected outcome, render exactly one task-evidence block as full content when safe or deterministic valid-UTF-8 beginning/recent-end excerpts with explicit untrusted middle omission when oversized, include the exact absolute authoritative path for full-file inspection, and budget the projection after all other prompt sections with a 4 KiB safety reserve below the 128 KiB boundary. Then render the absolute executable and workspace plus exact authorized origin into a shell-safe `notify --workdir ... --origin ... --message \"Hello there\"` command; the agent changes only the example message text. The ordinary CLI/API also exposes mutually exclusive `--recent-authorized` routing; it resolves only the newest user-active authorized conversation, returns only an event ID, and fails closed on multiple remote users, tied activity, revocation, unknown conversations, groups, or no eligible activity. The resolver and ordinary outbox delivery are primitives, never reminder policy.
- `/trigger` is the shared manual process interface: orchestrator passes retain serialized route ownership, and heartbeat requests enter the same non-overlapping primary scheduler as timed audits so manual completion resets the fixed delay. `/cleanup [days]` defaults to seven whole days and shares one cross-process operation with the primary-only eight-hour automatic cleanup, whose live retention setting defaults to 30 days. Cleanup uses strict older-than eligibility, protects every authenticated renewable live-TUI conversation lease (including transition grace) and every exact live job archive, serializes startup admission and resume branch creation-through-registration with history deletion, and remains fenced for one full live-lease duration after owner acquisition while attached clients renew into the replacement process. An ownerless plain-CLI cleanup also holds the election mutation lock through deletion and runs only when no primary lease exists outside the durable one-live-lease grace period after a clean release. Cleanup deletes only old histories and validated bounded job archives and moves only old terminal tasks unchanged into the cold unconfigured `tasks/archive` folder. Goal scanning and archiving share one boundary, and settled tasks remain live while linked to any nonterminal goal. Cleanup reports removed job files and bytes plus partial errors without touching active work or leases.
- `/task` and `/goal` append dedicated workspace Markdown directives to the normal communication-agent prompt; that agent creates or refines the durable document under the full workspace contract. They are not deterministic file-writing slash shortcuts.
- Enabled Telegram and WhatsApp transports require valid canonical sender allow-lists and fail closed at configuration, supervisor preflight, adapter startup, every live inbound event, and every outbound/provider boundary. Each adapter resolves the current list rather than trusting its constructor snapshot; missing, malformed, unavailable, or revoked authorization publishes a persistent error, terminates the active listener/socket, and is not reconnect-retried until configuration changes. Telegram teardown may call only `deleteWebhook` after revocation so a stopped listener is never left registered; all useful provider traffic remains blocked. Persisted credentials, sessions, Telegram identity mappings, prior event authorization, group addressing, and self-chat identity never grant access alone. Telegram may persist a minimal identity learned only from an allow-list-authenticated private inbound update so username-authorized users retain stable numeric proactive origins, but every application and delivery check must reapply the current allow-list and fail closed on absent or corrupt identity state.
- Telegram and WhatsApp deliver only the last non-continuing final response or terminal error for a remote message; streamed deltas, status events, and intermediate continuation responses remain visible only on streaming-capable local surfaces such as the TUI.
- The application emits one provider-neutral main communication-agent dispatch/terminal boundary consumed with overlap-safe, conversation-scoped reference semantics by the TUI, Telegram, and WhatsApp, including stalled-message recovery outside an inbound callback. Recovery routing preserves that dispatch boundary as the sole canonical owner, stops activity before terminal delivery, and never activates for scans that admit no provider turn. Ordinary Telegram messages still start visible user-turn activity at acceptance, including media/transcription preparation; slash commands wait for agent dispatch so framework-only commands remain inactive. WhatsApp translates only that canonical communication-agent lifecycle into composing, so media preparation, framework-only commands, and eventless intake remain inactive and every terminal response or handler error synchronously pauses after the final reference is released.
- Preserve in-flight communication turns when follow-up messages arrive. The latest message must receive a prompt response without silently abandoning still-relevant earlier coordination or taking ownership of long-running implementation work. When adjacent ordinary messages accumulate behind a queue-mode harness, dispatch them together in arrival order using the newest bounded prompt snapshot; never merge job controls across their validation and reservation boundaries.
- Job-scoped operator guidance uses the existing orchestrator session and emitter, treats delimited input as nonterminal data, preserves durable ownership and lifecycle tracking, bounds and deduplicates ordered delivery, and never equates acceptance or provider completion with a durable transition. A control message may cause at most one automatic continuation after exact owner/session/lease/document revalidation.
- Prefer standard-library dependencies unless a dependency materially improves reliability.
- Speech-enabled builds require CGO. Publish native release archives only for Linux amd64/arm64 and macOS amd64/arm64, with the matching sherpa-onnx and ONNX Runtime libraries included. Windows distribution is temporarily unsupported: release packaging and the npm launcher fail closed instead of compiling or downloading a Windows artifact.
- Keep vendored native-source and runtime license texts beside their owning source or under `third_party/`, and include them in release archives.
- The npm wrapper performs a ten-second update check only for interactive TUI starts, never for generated automatic-login services or noninteractive commands. It passes explicit periodic-check eligibility, the attempted lookup timestamp, and any valid latest version to the launched binary; an eligible npm-managed TUI reuses that snapshot, refreshes asynchronously no more than hourly, and shows a semantic warning triangle beside the header version only while a newer version is known. `/update` reports npm state through every channel; `/update install` stops the Go process before npm replaces it and then restarts through the supervising launcher.
- A published GitHub Release's `v`-prefixed semantic tag supplies the npm package version. Release preparation replaces the committed development placeholder and publishes the released root README with relative links pinned to that immutable GitHub tag.

## Verification

- Run `scripts/dev.sh dox` after changing repository structure or any `AGENTS.md`; the smoke test also runs this deterministic coverage and index gate through the pinned Go toolchain.
- Run `go test ./...`, `go vet ./...`, and `mkdir -p .tmp-bin && go build -o .tmp-bin/spynel ./cmd/spynel` before handoff after Go changes.
- Run `scripts/smoke.sh` after changes to initialization, configuration, harness dispatch, extension loading, channel lifecycle, or orchestration.
- Run `node npm/test.js` after npm launcher or release-layout changes.
- Run `scripts/package-native.sh` for the host target and execute the extracted archive after packaging or release-workflow changes; the release workflow compiles every supported target on a matching native runner.
- Ordinary Go test, race, vet, build, smoke, implementation, and review commands reuse Go's shared user cache. Do not assign `GOCACHE` to a project-local or per-command directory; Go action IDs already isolate flags, targets, tags, and toolchains.
- A deliberately requested cold-cache diagnostic must use `scripts/cold-cache.sh`, which creates a unique cache outside the project and removes it after the complete diagnostic process tree terminates. Cold-cache runs are for investigating suspected cache-dependent behavior, not routine verification.
- Write disposable verification binaries and profiles to test-managed temporary directories and clean them when the command finishes. If evidence must survive between implementation and review, keep it only under the ignored `.tmp-artifacts/<task-id>/` directory, record it in the task, and remove it when review no longer needs it.
- Use only purpose-specific repository-local `.tmp*` directories for developer toolchains, captures, scratch data, and temporary retained evidence. They are ignored disposable state and must remain safe to remove wholesale; never keep durable source or workflow state there.
